# 数据库设计

## 1. 约定与交付
MVP 采用 SQLite，建表文件为 [001_initial.sql](../database/migrations/001_initial.sql)。
正常运行由 `docker compose run --rm --no-deps migrate` 升级到 v2；启动时也会自动执行迁移服务。
原 db-init 只用于全新 v1 诊断库，拒绝覆盖已有数据库，不能替代正式版本迁移。
数据库存在 news-data 命名卷，容器路径 /app/data/news_assistant.db；由未来 api/worker 共享，
不再将宿主机 data 目录作为默认持久化位置。旧本地文件不会自动导入，迁移说明见[运行说明](07-Docker-Compose运行说明.md)。
当前为初始 DDL，不是已上线数据迁移系统；后续变更新增编号脚本与校验，不修改已发布版本。
已实现事务式 SQL 版本 runner 和 ORM 映射，不使用 create_all。
[002_run_sources.sql](../database/migrations/002_run_sources.sql) 新增 run_articles；识别已有 v1 并保留账号，幂等升级到 v2。

主键 TEXT UUID；布尔 INTEGER 0/1；时间 TEXT，应用统一输出 UTC ISO8601 固定毫秒 Z 后缀；
业务日期 YYYY-MM-DD，发送时刻 HH:MM。JSON 在应用边界校验，DDL 限制长度与状态；
不依赖所有 SQLite 构建都提供相同 JSON 扩展。每个连接必须开启 foreign_keys，
建议 WAL、busy_timeout=5000，单机本地磁盘部署，不把 SQLite 放网络共享盘。

## 2. 数据对象及关系
- users：认证账号，email 唯一、password_hash、enabled；管理员预置，不开放匿名注册。
- subscriptions：user_id 唯一；内容偏好 JSON、收件邮箱、验证时间、时区、调度状态与乐观锁 version。
- runs：生成任务、幂等键、订阅快照、窗口、预算计数、lease、草稿和错误；
  UNIQUE(subscription_id,idempotency_key)，一个订阅最多一个 queued/running。
- run_articles：run_id/article_id 复合主键及外键，记录本次可引用文章与证据级别。
- articles：规范 URL 唯一、原始 URL、来源、发布时间、正文、内容哈希和证据级别。
- tool_calls：每次实际调用或拒绝，保存序号、工具、脱敏参数、结果摘要、耗时和错误。
- briefs：正式简报；一个订阅每天唯一；指向成功 run，保存概述与正文。
- brief_items：简报条目、顺序、摘要、推荐理由、事件键；同简报位置与事件键均唯一。
- item_sources：条目与新闻多对多；保存证据级别，保留多个来源。
- deliveries：邮件 outbox；每个简报一个 email 投递，收件地址快照、Message-ID、状态和租约。
- delivery_attempts：每次发送的状态、时间、错误与 SMTP 回复码；序号唯一。
- schema_migrations：初始结构版本，用于识别数据库，不记录密钥。

外键：user → subscription → run → brief → item → source；
article ← source；brief → delivery → delivery_attempt；run → tool_call。
除 item_sources 外主体默认 RESTRICT 删除，清理通过显式业务流程，不级联删除历史审计。

## 3. 字段语义
订阅 topics_json、include_keywords_json、exclude_keywords_json 是字符串数组；
snapshot_json 保存本次完整可复现偏好，不包含密码或供应商配置。
run.started_at/finished_at 配合 status；deadline_at 为持久化期限，进程内使用单调时钟计时。
model_calls/tool_calls 是尝试次数，包含失败；token_usage_json 允许供应商无法返回用量。
briefs.run_id 唯一，brief 的订阅和业务日期通过复合外键与 run 保持一致。
brief_items.no_news 不单独设字段，brief.no_news=1 时由 Service 保证无条目。
正文由 items/sources 渲染为 Markdown/HTML，正文快照用于历史展示；链接仍以来源表为依据。
工具结果只存摘要，不记录隐藏推理或凭证；article 正文可到期置 NULL。

## 4. 状态机
生成：queued → running → succeeded / incomplete / failed。
queued 可取消，running 可在检查点取消为 cancelled；终态不原地重跑，创建新 run。
领取租约丢失的 running 任务终止 incomplete，避免恢复时重复发布。

投递：pending → sending → accepted / retry_wait / failed / unknown。
retry_wait → sending；pending/retry_wait → cancelled；
failed 可由授权请求重试为 pending；unknown 仅经核查和明确确认后重发。
CHECK 限制状态集合；合法状态转移由条件更新与 Service 控制，CHECK 不等同状态机。
delivery_attempt.status 为 sending/accepted/retryable_failure/failed/unknown；
遇到取消发生在网络发送中，优先保留外部真实状态，不能报告已撤回。

## 5. 并发与索引
- runs 部分唯一索引避免同订阅并行活动任务；定时重复用日幂等键兜底。
- briefs(subscription_id,business_date,edition) 避免同版本重复发布；edition=0 为每日正式版，普通手动请求复用；主动重新生成保存 edition>0。
- deliveries(brief_id,channel) 防重复创建邮件，message_id 唯一用于追踪。
- deliveries(status,next_attempt_at)、subscriptions(enabled,next_run_at) 支撑扫描。
- tool_calls(run_id,sequence)、delivery_attempts(delivery_id,attempt_no) 防审计序号重复。
- 不在等待模型、网页、SMTP 时持有事务。claim 用条件 UPDATE 并检查 rowcount。
- 发布 brief+items+sources+delivery 同事务；SMTP 在提交后发送，模糊结果不自动重试。

## 6. 数据保护与演进
收件地址属于个人数据，仅当前用户和授权运维可见，日志脱敏；备份遵守相同权限。
数据库不保存 SMTP 授权码、LLM 密钥、原始密码。开发与生产使用不同数据库文件。
正式迁移 PostgreSQL 时显式调整 UTC 类型、布尔、JSON、部分索引与锁行为，验证唯一约束。
升级先备份、迁移、校验完整性，再启动服务。当前初始化失败会回滚并删除本次新建空文件。
普通 docker compose down 保留数据；down -v 会删除卷。SQLite WAL 活跃时必须使用在线备份
或停止全部写入后备份，不能只复制主文件。卷文件由容器 UID/GID 10001 读写。

## 7. 验证
[check_design.py](../scripts/check_design.py) 在内存数据库执行初始 SQL，校验外键、每日唯一、
活动任务唯一、邮件唯一、跨订阅引用及非法状态，并检查本地文档链接和关键配置。
通过 docker compose run --rm check 统一运行；这验证设计与 DDL，
不替代未来 ORM、API、真实 SMTP 与并发 worker 集成测试。
